    Producten & diensten

    Laatst gecontroleerd tegen repo en git: 6 oktober 2026. Alle cijfers op deze site zijn gemeten (METEN = WETEN). De labels betekenen: PRODUCTION is dagelijks in gebruik en bewezen, WORKING betekent dat het werkt maar minder rijp is.

    Product 1: NoodleCore, de taal — PRODUCTION

    • De compiler verwerkt .nc → AST → NIR → C, en er is een tweede backend op LLVM. Twee onafhankelijke backends die bit-exact gelijk zijn: C haalt 240/240 stdlib-modules, LLVM 309/309, en de pitfall-suite is 18/18 gelijk.
    • Compileert zichzelf sinds mei 2026: de compiler maakt een nieuwe compiler die zichzelf weer identiek reproduceert. Dat is het criterium waaraan GCC moet voldoen. Alle 228 modules compileren via de eigen binary.
    • Ongeveer 4% sneller dan gemiddeld handgeschreven C: 95,9% van de C-tijd, gemeten over 11 scenario's.
    • De taalfuncties met bewijzen staan in features.md.

    Product 2: NoodleDB — PRODUCTION

    Uw database praat mee, welke u ook draait. NoodleDB is gebouwd om naast uw huidige database te draaien en er dan langzaam in te groeien. Applicaties op PostgreSQL en MySQL verbinden zonder dat u code aanpast. Data uit SQLite, PostgreSQL en MySQL importeert u met één commando. Aan de oude kant bent u niet vast aan een leverancier, aan de nieuwe kant hoeft u niets te herschrijven.

    Komt u van... U krijgt Bewijs
    PostgreSQL (en elke database die het PG-protocol spreekt) directe verbinding; elke PG-client werkt: psql, DBeaver, ORM's gemeten op 100k rijen: 3,4× sneller op graph-join, 5,5× op bulk-update, 6,8× op geïndexeerd zoeken
    MySQL / MariaDB import via mysqldump naar NDB; directe verbinding staat gepland importer: 120k rijen foutloos; MySQL-protocol verbonden (63/63 checks), querytijden gelijk aan of sneller dan via het PG-protocol
    SQLite / DuckDB (ingesloten) directe vergelijking: op alle 16 query-types sneller A/B op identieke machines
    CSV, JSON, losse bestanden import met één commando bewijs in de repo

    Eén engine, elke rol. De databasewereld verkoopt u vijf tot negen aparte producten. NoodleDB heeft die rollen als opslagmodellen ín de engine:

    Rol die u vandaag apart koopt Bekende merken In NoodleDB
    Relationele database Oracle, SQL Server, PostgreSQL, MySQL SQL, transacties en WAL (in productie)
    Graph-database Neo4j, ArangoDB BFS en Dijkstra ingebouwd (76/76)
    Vector-database Pinecone, Weaviate, pgvector HNSW-vector ingebouwd
    Zoeken, full-text Elasticsearch, Solr full-text ingebouwd (meerwoords-zoek, volgorde-exact)
    Tijdreeksen InfluxDB, TimescaleDB tijdreeksmodel in de engine
    Key-value, cache Redis, Memcached key-value-model in de engine
    Analytics op kolommen ClickHouse, Snowflake analytics-model in de engine

    Zeven producten, zeven licenties, zeven back-ups. Of één engine die de data niet hoeft te kopiëren tussen die rollen. Dat is de architectuurkeuze die in NDB_VISION_2030 vastligt: de engine kijkt hoe data gebruikt wordt en biedt het juiste model aan, zonder tussenlagen.

    • De complete engine is geschreven in NoodleCore zelf: parser (1.924 regels), executor, transacties, WAL, full-text, graph (BFS en Dijkstra, 76/76) en HNSW-vector.
    • SQL is de deur, niet het huis: relationeel, graph, vector en full-text zijn ingebouwde onderdelen van één engine, geen externe uitbreidingen.
    • Overname van bestaande data is bewezen op 190.267 rijen productiedata (count-edges 55× naar 391×, eq-text 9 tot 11×).
    • PG-compatibiliteit getest tegen een PostgreSQL-orakel: 128/128 regressietests.

    NoodleDB 2030: de database van de toekomst

    Elke database van vandaag was ooit een visie. Deze staat op papier en wordt per release gebouwd. Het volledige architectuurdocument met 25 ontwerpprincipes ligt in de repo. Hier de lijn, eerlijk verdeeld tussen wat al bewezen is en waar de engine heen gaat.

    Principe Status
    Meerdere modellen in één engine (relationeel, graph, vector, full-text) ✅ vandaag in productie
    Zelfgeschreven engine: parser, executor, transacties, WAL ✅ vandaag in productie
    Praten met klanten-databases (PG-wire, MySQL-import) en overnemen ✅ vandaag bewezen
    Adaptive Storage: de engine leert hoe data gebruikt wordt en kiest zelf, zoals id naar B-tree, namen naar gecomprimeerde kolommen, weinig gelezen data naar koude opslag, embeddings naar een vectorindex 🔭 architectuur vastgelegd, groeit per release
    Zelf-optimiserend: indexen aanmaken, plannen cachen, partitionering bijstellen op echte querypatronen 🔭 architectuur vastgelegd
    JIT-queries: SQL naar planner naar eigen compiler naar machine code 🔭 architectuur vastgelegd
    AI-native: VECTOR, TENSOR en embeddings als native datatypes, modellen naast hun data 🔭 deels vandaag (HNSW-vector)
    Time travel: elke tabel met geschiedenis, queries in de verleden tijd 🔭 architectuur vastgelegd
    De database zakt af tot onder het besturingssysteem 🔭 langetermijnlijn

    Waarom wij dit kunnen bouwen en anderen niet. Elke bestaande database moest een compiler náár de database brengen. NoodleDB is om een compiler heen gegroeid. Query-JIT, adaptive storage en zelf-optimisatie zijn voor ons geen nieuwe afhankelijkheid maar de kern die er al staat, opnieuw toegepast.

    Geen enkele visie-claim staat op deze site als factuur voor vandaag. Wat "✅" zegt is gemeten, wat "🔭" zegt is richting. Elke release die een 🔭 omzet in een ✅ komt met bewijs.

    Diensten: legacy-porting (het werk verkoopt zichzelf)

    Wij zetten uw bestaande broncode om naar leesbare, compileerbare C, heen én terug, met bewijs in plaats van beloften:

    • COBOL → NC → C: NIST-suite 459/459 geslaagd, retourweg bewezen, bank-demo bit-exact gelijk aan GnuCOBOL. Zie cobol-porting.md.
    • VB6, RPG en Fortran naar NC en C, met behoud van bedrijfslogica.
    • Trage Python-onderdelen naar NC: tot 3.000× sneller, gemeten (rekenwerk 3.049×).

    Zo werken we: gratis scan, dan een pilot die groen moet zijn of u betaalt niets, dan uitrol laag voor laag. Meer op cobol-porting.md of mail naar michael@noodlecore.io.
