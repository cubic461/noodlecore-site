    Examples

    Seeing is better than believing. The same code in two languages side by side, with the measured gain underneath. All numbers come from our benchmark reports, no estimates — and what stands here is exactly what was measured.

    Example 1: arithmetic loop (summing 10 million numbers)

    A classic arithmetic loop: the same algorithm, two languages. This shows what compilation to native C delivers without changing anything yourself.

    Python

    def loop_sum(n):
    total = 0
    for i in range(n):
        total += i
    return total

print(loop_sum(10_000_000))

    NoodleCore

    fn loop_sum(n: int) -> int {
    var total = 0
    var i = 0
    while i < n {
        total = total + i
        i = i + 1
    }
    return total
}

    Measured result (iMac Pro, fastest of 3 runs; C side with -O3 -march=native)

    Language Time Speedup
    Python (CPython 3.11) 609.1 ms —
    NoodleCore → C 17.2 ms 35.4× faster

    How much you win grows with the share of pure computation. Our heaviest compute benchmark (arithmetic, 1 million iterations) measures 51,826 ms in Python against 17 ms native — 3,049×. That is a different test than the one above; all Python comparisons are listed together on the Language features page.

    Example 2: the language's own tax (NC versus hand-written C)

    The question behind every "fast language": how much does the language itself cost? For NoodleCore this is measured case by case against hand-written C, with the same compile flags (-O3 -march=native). Here is the string-append test: appending one character to a string, 100,000 times.

    NoodleCore

    fn append_100k() -> str {
    var s = "x"
    var i = 0
    while i < 100000 {
        s = s + "x"
        i = i + 1
    }
    return s
}

    Hand-written C

    #include <stdio.h>
#include <string.h>

int main(void) {
    char buf[100001];
    memset(buf, 'x', 100000);
    buf[100000] = 0;
    printf("%zu\n", strlen(buf));
    return 0;
}

    Measured result (iMac Pro, fastest of 3 runs; C side with -O3 -march=native)

    Language Time Ratio
    Python (CPython 3.11) 8.4 ms —
    Hand-written C 5.0 ms 1.7× faster than Python
    NoodleCore → C 5.1 ms 1.6× faster than Python

    Three languages, one test — and the core of the story: NC (5.1 ms) sits within 2% of hand-written C (5.0 ms), while Python needs 68% more time than C. The layer between Python and C disappears entirely; the tax being paid is Python's own.

    Example 3: database (NoodleDB versus SQLite)

    The third pillar: the database lives inside the language. The same question over the same data — 1 million order lines — A/B measured: Python with SQLite against NoodleCore with NoodleDB. Here is the first row of the table: the average amount per status group.

    Python + SQLite

    import sqlite3

con = sqlite3.connect("orderlines.db")
rows = con.execute(
    "SELECT status, AVG(bedrag) FROM orderlines"
    " GROUP BY status ORDER BY status"
).fetchall()

    NoodleCore + NoodleDB

    use noodledb_sql

fn main() -> int {
    db = ndb_open("orderlines.ndb")
    ndb_exec(db,
        "SELECT status, AVG(bedrag) FROM orderlines" +
        " GROUP BY status ORDER BY status")
    return 0
}

    Measured (iMac Pro, 1 million rows, median of 5 runs — 20 October 2026)

    Query SQLite NoodleDB Gain
    Average per group (AVG + GROUP BY) 988.0 ms 545.4 ms 1.8× faster
    Count in range (COUNT + WHERE) 126.9 ms 80.7 ms 1.6× faster
    Count on customer range (COUNT + WHERE) 60.5 ms 57.6 ms 1.05× faster

    Example 4: four databases, one measuring stick

    Being compatible is one thing; being measurably fast is another. The same query, the same data, on the same machine - but now four engines side by side: NoodleDB, PostgreSQL 18, SQLite and DuckDB. One benchmark suite, median of 5 runs, correctness hard-checked per query.

    No cherry-picking: the table also shows the classes where NoodleDB does not win yet - the full improvement track is noted below.

    (iMac Pro, 100,000 rows (seed 42), median of 5 runs — 2026-10-29. System load during the measurement 4.0-4.5 (guideline < 3; macOS background indexing). All four engines faced the same load: PostgreSQL, SQLite and DuckDB measure within a few percent of their earlier figures, so the relative standings hold.)

    The cost of the wire protocol

    NoodleDB also speaks the PostgreSQL and MySQL wire protocols. Same engine, same data, but now over the network protocol, like a regular database client:

    Query NoodleDB direct NDB via Postgres protocol NDB via MySQL protocol
    Bulk load 100k rows 182 163 160
    Point lookup (PRIMARY KEY) 0.00 0.06 0.16
    Range scan (WHERE BETWEEN) 0.25 0.34 0.36
    2-table join 0.73 3.57 0.85
    3-table join * 0.94 3.96 1.17
    GROUP BY + COUNT + AVG 0.31 1.92 0.41
    Text search LIKE 0.42 0.53 0.58
    2-hop graph count (self-join) 1.05 4.47 1.29
    Indexed text search 0.29 - -
    10k UPDATEs in 1 transaction 56.4 - -

    * 3-table join: NoodleDB executes the nested form (two hash joins), the other engines the flat form - same result, same data. The flat 3-join is a known optimization track.

    Where NoodleDB wins: every read class - range scans (28x vs PostgreSQL, 47x vs SQLite), joins (12-22x), aggregates (51x vs PostgreSQL, 141x vs SQLite), 2-hop graph counts (42x vs PostgreSQL, 74x vs SQLite), text search (27-30x) and indexed text search. Where the others still win: bulk loading (1.5x) and small updates (1.5x), both versus SQLite - and over the wire protocols, point lookups trail SQLite's in-process call. That is exactly the improvement track.

    The wire-protocol table shows the same NoodleDB engine over the PostgreSQL and MySQL protocols, measured against servers written and compiled in NoodleCore itself: no Python in the hot path. Both protocols run range scans within 0.1 ms of direct access and even load 100k rows faster than the direct path; the MySQL protocol keeps joins and aggregates within 1.4x of direct. What remains: point lookups pay the roundtrip (0.06-0.16 ms) and over the PostgreSQL protocol DuckDB edges ahead on joins - that is the improvement track.

    Example 5: the heaviest join — self-join on 1 million rows

    The self-join was the deepest gap of the entire campaign: 194.8× slower than SQLite. After the acceleration of 21 October 2026 the same query on the same machine runs in 42.12 ms — 3.3× faster than SQLite (139.58 ms), with an identical row count.

    This is not an isolated measurement but the campaign's gate: all 16 heaviest query shapes were measured together after the fix, and every single one is now faster than SQLite. Correctness strictly checked per query (rows 1/1 up to 632,117/632,117 exactly matching the oracle).

    (iMac Pro, 1 million rows, median of 5 runs, 21 October 2026)

    Query NoodleDB SQLite NDB faster
    Self-join on 1 million rows 42.12 139.58 3.3×
    Heaviest aggregation (632,117 groups) 390 1167 3.0×
    Full gate (16 query shapes) 16/16 faster — —

    The three classes that still lose to DuckDB on the 100k benchmark (range scans, flat joins, GROUP BY) remain on the improvement track — phase 2 of the campaign is running now.

    An honest caveat

    The gain depends on the kind of work: the more pure computation and the heavier Python's interpreter tax, the bigger the win. Scripts that mostly wait on disk or network gain little. That is why we port the slow parts, not whole programs, and why we publish the method behind every claim.
