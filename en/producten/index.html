    Product 1: NoodleCore, the language — PRODUCTION

    • The compiler processes .nc → AST → NIR → C, with a second backend on LLVM. Two independent backends that are bit-exact identical: C handles 240/240 stdlib modules, LLVM 309/309, and the pitfall suite matches 18/18.
    • It has compiled itself since May 2026: the compiler produces a new compiler that reproduces itself identically again. That is the criterion GCC is held to. All 228 modules compile via their own binary.
    • Roughly 4% faster than average hand-written C: 95.9% of C's runtime, measured across 11 scenarios.
    • The language features with their proofs are on features.md.

    Product 2: NoodleDB — PRODUCTION

    Your database gets a say, whichever one you run. NoodleDB is built to run next to your current database and grow into it gradually. Applications on PostgreSQL and MySQL connect without changing your code. Data from SQLite, PostgreSQL and MySQL imports with a single command. On the old side you're not locked to one vendor; on the new side there's nothing to rewrite.

    Coming from... You get Proof
    PostgreSQL (and every database speaking the PG protocol) direct connection; every PG client works: psql, DBeaver, ORMs measured on 100k rows: 3.4x faster on a graph join, 5.5x on bulk update, 6.8x on indexed lookup
    MySQL / MariaDB import via mysqldump into NDB; direct connection is planned importer: 120k rows error-free; MySQL protocol connected (63/63 checks), query times equal to or faster than over the PG protocol
    SQLite / DuckDB (embedded) direct comparison: up to 1.8× faster per query type A/B on identical machines
    CSV, JSON, loose files import with one command proof in the repo

    One engine, every role. The database world sells you five to nine separate products. NoodleDB has those roles as storage models ínside the engine:

    Role you buy separately today Known brands In NoodleDB
    Relational database Oracle, SQL Server, PostgreSQL, MySQL SQL, transactions and WAL (in production)
    Graph database Neo4j, ArangoDB BFS and Dijkstra built in (76/76)
    Vector database Pinecone, Weaviate, pgvector HNSW vector built in
    Search, full-text Elasticsearch, Solr full-text built in (multi-word search, order-exact)
    Time series InfluxDB, TimescaleDB time-series model in the engine
    Key-value, cache Redis, Memcached key-value model in the engine
    Columnar analytics ClickHouse, Snowflake analytics model in the engine

    Seven products, seven licenses, seven backups. Or one engine that never has to copy data between those roles. That is the architecture choice laid down in NDB_VISION_2030: the engine watches how data is used and offers the right model, without intermediate layers.

    • The complete engine is written in NoodleCore itself: parser (1,924 lines), executor, transactions, WAL, full-text, graph (BFS and Dijkstra, 76/76) and HNSW vector.
    • SQL is the door, not the house: relational, graph, vector and full-text are built-in parts of one engine, not external extensions.
    • Taking over existing data is proven on 190,267 rows of production data (count-edges 55x to 391x, eq-text 9 to 11x).
    • PG compatibility tested against a PostgreSQL oracle: 128/128 regression tests.

    NoodleDB 2030: the database of the future

    Every database of today was once a vision. This one is on paper and gets built release by release. The full architecture document with 25 design principles is in the repo. Here is the line, honestly split between what is already proven and where the engine is going.

    Principle Status
    Multiple models in one engine (relational, graph, vector, full-text) ✅ in production today
    Self-written engine: parser, executor, transactions, WAL ✅ in production today — crash durability proven at SQLite level: 10/10 kill scenarios recovered bit-exact, 1,000 consecutive crash-recovery cycles 100% correct
    Talking to customer databases (PG-wire, MySQL import) and taking over ✅ proven today
    Consensus and replication across multiple nodes (Raft, CDC over TCP) ✅ proven — 3-node Raft cluster on real hardware (three machines over TCP), 500/500 quorum commits, new leader after a kill in 222 ms
    Adaptive Storage: the engine learns how data is used and chooses itself — id to a B-tree, names to compressed columns, rarely-read data to cold storage, embeddings to a vector index 🚧 in development — coupled to the executor via the self-learning index loop; planner integration is the next building block
    Self-optimizing: creating indexes, caching plans, adjusting partitioning on real query patterns 🚧 first closed loop proven — the engine places indexes itself as soon as a query pattern repeats, measures before/after and rolls back if it doesn't pay off (5.3x measured on a real pattern); extending to partitioning is planned
    JIT queries: SQL to planner to own compiler to machine code ✅ proven — 25.6x faster than the interpreter path, measured in an A/B test, with automatic fallback to the interpreter; not enabled by default yet
    Vectorized execution: column-wise computing in SIMD batches for analytics ✅ proven — 2.1x–2.4x faster on analytics queries over 1 million rows; a group-by over 632,117 groups dropped from over 40 minutes to 1.7 seconds
    AI-native: VECTOR, TENSOR and embeddings as native datatypes, models next to their data 🔭 partly today (HNSW vector)
    Time travel: every table with history, queries in the past tense 🔭 architecture laid down
    NoodleLinux: the database sinks beneath the operating system — the OS storage layer itself runs on the engine 🔭 long-term line; first step (manageable Linux module) proven

    Why we can build this and others can't. Every existing database has to bring a compiler ínto the database. NoodleDB grew around a compiler. Query JIT, adaptive storage and self-optimization are no new dependency for us but the core that already exists, applied anew. The build order that stood here — first crash durability at SQLite's level, then the vectorized executor, then the self-optimizing layer — was completed in October 2026 and delivered step by step with measurements.

    No vision claim on this site is an invoice for today. What says "✅" is measured, what says "🚧" is in development and what says "🔭" is direction. Every release that turns a 🚧 or 🔭 into a ✅ arrives with proof.

    Services: legacy porting (the work sells itself)
