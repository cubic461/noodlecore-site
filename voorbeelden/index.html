    Voorbeelden

    Zelf kijken is beter dan geloven. Dezelfde code in twee talen naast elkaar, met de gemeten winst eronder. Alle cijfers komen uit onze benchmarkrapporten, geen schattingen. Wat hier staat, is precies wat gemeten is.

    Voorbeeld 1: reken-loop (10 miljoen getallen sommeren)

    Een klassieke reken-loop: hetzelfde algoritme, twee talen. Zo zie je wat compilatie naar native C oplevert zonder dat je zelf iets verandert.

    Python

    def loop_sum(n):
    total = 0
    for i in range(n):
        total += i
    return total

print(loop_sum(10_000_000))

    NoodleCore

    fn loop_sum(n: int) -> int {
    var total = 0
    var i = 0
    while i < n {
        total = total + i
        i = i + 1
    }
    return total
}

    Gemeten resultaat (iMac Pro, snelste van 3 runs; C-zijde met -O3 -march=native)

    Taal Tijd Snelheidswinst
    Python (CPython 3.11) 609,1 ms —
    NoodleCore → C 17,2 ms 35,4× sneller

    Hoeveel je wint groeit met het aandeel zuiver rekenwerk. Onze zwaarste rekenmeting (arithmetic, 1 miljoen iteraties) meet 51.826 ms in Python tegen 17 ms native: 3.049×. Dat is een ándere test dan hierboven; alle Python-vergelijkingen staan samen op de Taalfeatures-pagina.

    Voorbeeld 2: de tol van de taal zelf (NC tegen handgeschreven C)

    De vraag achter elke "snelle taal": hoeveel kost de taal zélf? Voor NoodleCore is dat geval voor geval gemeten tegen handgeschreven C, met dezelfde compile-vlaggen (-O3 -march=native). Hier de string-append-test: 100.000 keer een teken achter een string plakken.

    NoodleCore

    fn append_100k() -> str {
    var s = "x"
    var i = 0
    while i < 100000 {
        s = s + "x"
        i = i + 1
    }
    return s
}

    Handgeschreven C

    #include <stdio.h>
#include <string.h>

int main(void) {
    char buf[100001];
    memset(buf, 'x', 100000);
    buf[100000] = 0;
    printf("%zu\n", strlen(buf));
    return 0;
}

    Gemeten resultaat (iMac Pro, snelste van 3 runs; C-zijde met -O3 -march=native)

    Taal Tijd Verhouding
    Python (CPython 3.11) 8,4 ms —
    Handgeschreven C 5,0 ms 1,7× sneller dan Python
    NoodleCore → C 5,1 ms 1,6× sneller dan Python

    Drie talen, één test, en de kern van het verhaal: NC (5,1 ms) zit binnen de 2% van handgeschreven C (5,0 ms), terwijl Python 68% meer tijd nodig heeft dan C. De taal tussen Python en C valt volledig weg; de tol die betaald wordt, is die van Python zelf.

    Voorbeeld 3: database (NoodleDB tegen SQLite)

    De derde pijler: de database zit in de taal. Dezelfde vraag over dezelfde data (1 miljoen orderregels), A/B gemeten: Python met SQLite tegen NoodleCore met NoodleDB. Hieronder de eerste regel uit de tabel: het gemiddelde bedrag per statusgroep.

    Python + SQLite

    import sqlite3

con = sqlite3.connect("orderlines.db")
rows = con.execute(
    "SELECT status, AVG(bedrag) FROM orderlines"
    " GROUP BY status ORDER BY status"
).fetchall()

    NoodleCore + NoodleDB

    use noodledb_sql

fn main() -> int {
    db = ndb_open("orderlines.ndb")
    ndb_exec(db,
        "SELECT status, AVG(bedrag) FROM orderlines" +
        " GROUP BY status ORDER BY status")
    return 0
}

    Gemeten (iMac Pro, 1 miljoen rijen, mediaan van 5 runs — 20 oktober 2026)

    Vraag SQLite NoodleDB Winst
    Gemiddelde per groep (AVG + GROUP BY) 988,0 ms 545,4 ms 1,8× sneller
    Telling in bereik (COUNT + WHERE) 126,9 ms 80,7 ms 1,6× sneller
    Telling op klantbereik (COUNT + WHERE) 60,5 ms 57,6 ms 1,05× sneller

    Voorbeeld 4: vier databases, één meetlat

    De tol van het protocol

    NoodleDB spreekt ook de draadprotocollen van PostgreSQL en MySQL. Dezelfde engine, zelfde data, maar nu over het netwerkprotocol zoals een gewone databaseclient:

    Vraag NoodleDB direct NDB via Postgres-protocol NDB via MySQL-protocol
    Inladen 100k rijen 472 2807 15156
    Punt-opzoeking (PRIMARY KEY) 0.05 0.24 0.37
    Bereik-scan (WHERE BETWEEN) 19.0 19.0 17.7
    Join over 2 tabellen 45.8 46.4 49.5
    Join over 3 tabellen * 64.6 64.0 67.3
    GROUP BY + COUNT + AVG 5.05 11.4 5.2
    Tekstzoeken LIKE 3.57 36.3 4.3
    2-hop graaftelling (self-join) 13.1 14.9 13.7
    Geïndexeerd tekstzoeken 0.28 - -
    10k UPDATEs in 1 transactie 161 - -

    * Join over 3 tabellen: NoodleDB voert de geneste vorm uit (twee keer hash-join), de overige engines de platte vorm: dezelfde uitkomst, dezelfde data. De platte 3-join is een bekend optimalisatie-traject.

    Stand na de join-versnelling van 21–22 oktober (avondmeting): tegen PostgreSQL wint NoodleDB alle 11 gemeten klassen. Tegen SQLite wint NoodleDB 8 van 11; SQLite blijft voor op inladen, punt-opzoeken en kleine updates. Tegen DuckDB wint NoodleDB 7 van 9; DuckDB houdt GROUP BY en tekstzoeken. De maatstaf waar het verbetertraject op richt is DuckDB (GROUP BY, tekstzoeken, de platte 3-join) én de resterende SQLite-klassen — dat is fase 2 van de campagne, die nu loopt en vandaag al bereik-scan (18,5 → 0,33 ms), join-2 (3,12 → 0,80 ms), de geneste 3-join (26,4 → 1,21 ms) en de 2-hop graaftelling (14,6 → 1,20 ms) omsloeg.

    De draadprotocol-tabel toont dezelfde NoodleDB-engine via het PostgreSQL- en MySQL-protocol: dezelfde queries, maar nu betaal je de vertaling en de retourtijd. Na de protocol-fix van 21 oktober 2026 betalen beide draadroutes alléén nog de vertaal- en framing-vloer van het protocol zelf: punt-opzoekingen via het MySQL-protocol werden 245× sneller (90,9 ms → 0,37 ms), en de minimale vraag meet via het PostgreSQL-protocol een draadlaag van 0,24 ms. Zwaardere vragen zijn engine-bound: dezelfde cijfers als directe toegang, geen extra protocolverlies.

    Voorbeeld 5: de zwaarste join — zelf-join op 1 miljoen rijen

    De zelf-join was het diepste gat van de hele campagne: 194,8× trager dan SQLite. Na de versnelling van 21 oktober 2026 draait dezelfde vraag op dezelfde machine in 42,12 ms — 3,3× sneller dan SQLite (139,58 ms), met identiek uitkomstrijen-aantal.

    Dit is géén losse meting maar de poort van de campagne: alle 16 zwaarste queryvormen zijn na de fix samen gemeten, en élke vorm is nu sneller dan SQLite. Correctheid per query streng gecontroleerd (rijen 1/1 tot 632.117/632.117 exact gelijk aan het orakel).

    (iMac Pro, 1 miljoen rijen, mediaan van 5 runs, 21 oktober 2026)

    Vraag NoodleDB SQLite NDB sneller
    Zelf-join op 1 miljoen rijen 42,12 139,58 3,3×
    Zwaarste aggregatie (632.117 groepen) 390 1167 3,0×
    Volledige poort (16 queryvormen) 16/16 sneller — —

    De drie klassen die op de 100k-meetlat nog verliezen van DuckDB (bereik-scan, platte joins, GROUP BY) staan open op het verbetertraject — fase 2 van de campagne loopt nu.

    Eerlijke kanttekening

    De winst hangt af van het soort werk: hoe meer zuiver rekenwerk en hoe zwaarder de tolkosten van Python, hoe groter de winst. Scripts die vooral op de schijf of het netwerk wachten, winnen weinig. Daarom porten wij de trage delen, geen hele programma's, en daarom publiceren wij per claim de methodiek.
